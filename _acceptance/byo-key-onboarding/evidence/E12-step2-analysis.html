NEW root cause: the client-side SSE handler used by every ABI node execute path drops this message

Every ABI-driven node (via AbiNodeShell → useAbiExecution().run()) creates its task through createBatchTasks() in useBatchTaskManager (src/hooks/use-task.ts), NOT through the sibling hook useTaskSubscription used elsewhere in the same file. The two hooks build the client-side Task.error field differently from the same wire shape:

// useTaskSubscription (src/hooks/use-task.ts ~line 408) — CORRECT, falls back to data.error:
error: message.error || ((message.data as Record<string, unknown>)?.error as string),

// useBatchTaskManager (src/hooks/use-task.ts ~line 724) — BUG, no fallback:
error: message.error,

The SSE wire message (TaskEvent, see src/lib/task/emitter.ts / src/types/sse.ts) has NO top-level error field at all — only data.error ever carries text (set by notifyTask(taskId, status, data, nodeId) in both branches of src/lib/task/runner.ts). So message.error (top-level) is always undefined for every task that goes through this path, which is EVERY execute-button run on an ABI node — not specific to OpenAI or to this one plugin. internalTask.error therefore ends up undefined, envKeyFromFailure(task) sees task.error ?? "" === "", classifyFailure("") returns {kind: "none"}, and useNodeKeyGate().noteTask() never calls setEnvKey/setState({phase:"needs-key"}). NodeKeyPrompt never mounts ({keyGate.envKey ? <NodeKeyPrompt .../> : null} stays null forever).

This also explains the generic toast visible in E12-step2.png/step3.png ("Task failed" / "Task execution failed", no "Enter key" action button): task-failure-toaster.tsx reads data?.message?.trim() || data?.error?.trim() from the SSE payload directly (not through the buggy hook), but the catch-block path in runner.ts sets data.message to the LITERAL generic string "Task execution failed" (a second, independent issue: message wins the || over the specific data.error, so even the toast's own classifyFailure call gets the wrong string on that particular code path). The pre-flight required-key check specifically hits this catch block (it throws before reaching the result.success === false branch), so the missing-key case is the worst-hit one: neither the toast nor the node ever names the key.
