E12 (AC-9) — why steps 2 and 3 could not be captured as PNG frames

Why capture.ui (pnpm ui:capture) can't produce these frames: it navigates puppeteer to a URL and screenshots a fresh page load. The "needs-key" node state (KeyPromptState in src/components/workspace/node-key-prompt.tsx, driven by useNodeKeyGate() in src/components/workspace/nodes/base/abi-node-shell.tsx) is transient React client state set only when a live task-update callback fires during the same browser session that triggered the run (noteTask() → setEnvKey/setState). It is not persisted server-side, so a fresh navigation never reproduces it. This is a real limitation of the reference capture script for this specific AC, not a workaround I chose for convenience.

What I did instead: drove the real UI/task pipeline directly and inspected the real result

  1. With the onboarding example loaded and previously verified working (Add Video → Split Video → Concat Video completing with zero keys using the "(local)" plugin variants), I switched the Split Video node's Implementation dropdown from "PySceneDetect (local)" to "PySceneDetect" — the Modal-backed tongflow-modal-pyscenedetect plugin, whose tongflow.plugin.json declares MODAL_TOKEN_ID and MODAL_TOKEN_SECRET as "required": true. Both are blank in .env. This is the only plugin actually installed in this repo (plugins/) that declares a required key — confirmed by grepping every installed plugin's tongflow.plugin.json for "required": true.
  2. I clicked "Start Slice" to run it. This created a real task against the real Modal SDK, which failed for lack of credentials (verified independently via GET /api/task/list, saved to evidence/E12-real-task-list.json).
  3. The real, repeated (5 separate real runs across this verify session) task.error text is: 
    downloading weights failed (exit 1): ╭─ Error ──────────────────────────╮
│ Token missing. Could not authenticate client. If you have token credentials, │
│ see modal.com/docs/sdk/py/latest/config for setup help. If you are a new     │
│ user, register an account at modal.com, then run `modal token new`.          │
╰──────────────────────────────────────────────────────────────────────────────╯

Why this real failure does not (and, per the regex, structurally cannot) drive the node into "needs-key"

src/components/workspace/nodes/base/abi-node-shell.tsx:

const KEY_FAILURE_PATTERN =
    /(missing|invalid|unauthorized|not set|401|403|thiếu khoá|sai khoá)/i;
const ENV_KEY_PATTERN =
    /\b([A-Z][A-Z0-9]*(?:_[A-Z0-9]+)*_(?:API_KEY|KEY|TOKEN|SECRET))\b/;

function envKeyFromFailure(task: Task): string | null {
    const message = task.error ?? "";
    if (!KEY_FAILURE_PATTERN.test(message)) return null;
    return ENV_KEY_PATTERN.exec(message)?.[1] ?? null;
}

Applying this to the real message above: KEY_FAILURE_PATTERN matches ("Token missing"), but ENV_KEY_PATTERN requires an ALL-CAPS, underscore-separated token ending in _API_KEY/_KEY/_TOKEN/_SECRET literally present in the message. The real Modal CLI error text never names MODAL_TOKEN_ID or MODAL_TOKEN_SECRET — it only says "Token missing." in prose. So ENV_KEY_PATTERN.exec() returns null, envKeyFromFailure() returns null, and noteTask() takes its early return (if (!key) return;) without ever calling setState({ phase: "needs-key" }). The node stays in its default/idle key-gate state; NodeKeyPrompt never renders ({keyGate.envKey ? <NodeKeyPrompt ... />: null}, and envKey is never set).

I watched this live in the Browser pane after triggering the run: the Split Video node went through its normal "running → failed" cycle and returned to its plain idle card — no amber "Bước này cần một khoá API" panel, no inline input, appeared on the node. (A generic failure indicator/toast is a separate code path — AC-11/E15 — not this AC.)

Step 3 (enter the key at the node) — never reachable

Because step 2's needs-key panel never appears for this real failure, there is no inline form to type a key into. Step 3 could not be performed against the real pipeline. No settings dialog was opened at any point during this specific sequence (separately confirmed by not touching Settings during these particular actions).

Caveat: shared dev environment

This verify session ran against a dev server/workspace/plugins directory that was being concurrently mutated by other agents in the same batch (nodes appearing/disappearing, an unrelated "Internal Server Error" HMR blip, and — critically — plugins/tongflow-modal-pyscenedetect and plugins/tongflow-modal-ffmpeg being deleted from disk partway through this session by another process, which is why the Implementation dropdown later showed only the local option). This made a clean, race-free PNG capture of the exact "Modal implementation selected" moment impractical after that point. The conclusion above does not depend on that instability, however — it rests on (a) the plugin's own declared "required" env keys, (b) five independent real task-failure records with identical error text, and (c) direct reading of the current abi-node-shell.tsx regex logic against that exact text.
